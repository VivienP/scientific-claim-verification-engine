# Launch Readiness Audit

## Concern 1 — Benchmark data provenance

**Verdict:** **confirmed issue (red)**

**Evidence:**

Real-tool input files in `examples/inputs/`:

| File | Lines | Source | Citations? | Run end-to-end? |
|---|---|---|---|---|
| `crow_sample.txt` | **1** | Synthetic NLP prose (Wei 2022, Hoffmann 2022, Brown 2020) | yes | no saved report |
| `edison_trem2_alzheimer.txt` | 60 | Edison Scientific Literature (real) | yes | yes (×3) |
| `gemini_sample.txt` | 183 | Gemini-generated review on psilocybin | no inline citations | no saved report |

`scripts/fetch_crow_sample.py` exists to fetch a real FutureHouse Crow output but the saved `crow_sample.txt` is a 1-line synthetic placeholder, not a real Crow answer.

Saved reports under `reports/runs/`:

```text
reports/runs/14ede71b-9f42-4302-96f5-ba1a2b215a5f/report.json   (21 claims, Edison TREM2)
reports/runs/5163784a-e990-4c7a-bc9f-1418f4d199b8/report.json   (20 claims, Edison TREM2)
reports/runs/c17dfd93-742b-463d-aebe-e7914bb1b6c5/report.json   (21 claims, Edison TREM2)
```

All three runs are on the **same** Edison TREM2 input. Aggregated summary fields:

| Run | total | supported | unsupported | not_addressed | partially_supported |
|---|---|---|---|---|---|
| 14ede71b | 21 | 0 | 1 | 18 | 2 |
| 5163784a | 20 | 0 | 1 | 18 | 1 |
| c17dfd93 | 21 | 0 | 1 | 18 | 2 |
| **Total** | **62** | **0** | **3** | **54** | **5** |

`grep "fulltext_verified|verification_depth" reports/` returned 0 matches — none of these reports were generated by the Phase 1 full-text path (`verify_claim_fulltext`). All three predate Phase 1 implementation.

`grep -ric "futurehouse|answerthis|elicit|consensus|sakana|iris.ai|crow|falcon|owl|phoenix" README.md` → **0**.

No `benchmarks/`, `data/`, or `tests/fixtures/` directories exist.

**Findings:**

The repo does not contain real outputs from AnswerThis, FutureHouse Crow/Falcon, Elicit, Consensus, Sakana, or Iris.ai that have been verified end-to-end and committed. Only one real-tool output (Edison Literature on TREM2) has ever been processed, and it produced 0 supported / 3 unsupported / 54 not_addressed / 5 partially_supported across three duplicate runs of ~21 unique claims. The dominant verdict is `not_addressed` (87%), which the README itself attributes to abstract-only verification — a structural artifact, not evidence of hallucination. The launch hook *"X% of cited claims unsupported in real outputs from [tools]"* cannot be supported by current data: the unsupported rate is too low (1/21 ≈ 5%), the tool diversity is one (Edison only), the runs are duplicates, and none used the Phase 1 full-text path. No numeric inconsistencies have been flagged because that engine does not exist.

**Recommended fixes (prioritized):**

1. **(P0, ~2h)** Run `verify_claim_fulltext` on the existing Edison TREM2 input and commit the report.
2. **(P0, ~1h)** Run `scripts/fetch_crow_sample.py` against a real FutureHouse Crow API to replace the 1-line synthetic placeholder.
3. **(P0, ~2h)** Add at least 1 more tool: AnswerThis, Elicit, or Consensus. Aim for ≥3 distinct AI-for-science tools, ≥20 aggregated claims, ≥3 documented unsupported verdicts, ≥1 numeric inconsistency.
4. **(P1, ~30 min)** Create `benchmarks/real_outputs/` with subdirectories per tool, each containing `input.txt`, `meta.json`, and `report.json`. Reference this directory from the README headline.

## Concern 3 — Numeric engine worked example

**Verdict:** **confirmed issue (red — feature does not exist yet)**

**Evidence:**

```text
Glob src/numeric*       → No files found
Glob src/**/numeric*    → No files found
```

`grep -ric "scipy|statsmodels|p_value|effect_size|sample_size"` on `src/` returned 3 matches — none are an actual deterministic comparison engine.

README explicitly lists Phase 2 in the **Future work** section.

**Findings:**

The numeric engine is not implemented. The launch hook *"flags numerical inconsistencies (p-values, sample sizes, effect sizes)"* cannot be supported. The structured JSON report has no `numeric_consistency` field, no before/after numbers, no surfacing for non-technical readers.

The Edison TREM2 input is rich with verifiable numeric assertions that would make excellent worked-example candidates:

| Candidate claim | Source paper | DOI | What to check |
|---|---|---|---|
| "oA β1-42 bound sTREM2-Fc with KD = 86.50 nM" | Zhong 2018 | 10.1186/s13024-018-0247-7 | Does the paper actually report 86.50 nM? |
| "39% of WT vs 11.5% of KO microglia responded to SDF-1α" | McQuade 2020 | 10.1038/s41467-020-19227-5 | Cross-check both percentages |
| "ARM were 77.5% in A+T− vs 7.8% in A−T− (OR 40.53, 95% CI 23.58-73.71)" | Nguyen 2020 | 10.1007/s00401-020-02200-3 | Internal consistency: OR vs CI |
| "p < 0.0001 with n = 3" | Zhong 2018 | 10.1186/s13024-018-0247-7 | Statistical plausibility check given n=3 |

The third candidate is the strongest — the OR / CI / proportions in a single claim allow a fully internal arithmetic check (no LLM dependency) and would showcase the deterministic-engine moat.

**Recommended fixes (prioritized):**

1. **(P0 if launching with the numeric claim, ~1 day)** Build a minimal numeric engine with one OR/CI consistency check. Use the Nguyen 2020 ARM claim as the worked example.
2. **(P0 if not building Phase 2 now, ~5min)** Remove "numerical inconsistencies (p-values, sample sizes, effect sizes)" from the launch hook.
3. **(P1, ~15min)** Once numeric engine ships, surface findings in the report JSON as `verification.numeric_check: {claim_value, source_value, tolerance, consistent, explanation}`.

## Overall launch-readiness verdict

**RED.**

The project's engineering is in good shape (Phase 1 shipped clean: 173 tests, mypy strict, ruff clean, F1=0.94 baseline preserved). The launch readiness is not. Three of the four launch hook ingredients are absent or stale: (1) no real-tool benchmark beyond a single duplicated Edison run; (2) no numeric engine, despite the launch hook implying one exists; (3) README documents Phase 0 only and lacks the "why it matters" framing and the design-partner CTA. A launch in this state will either undersell the actual capability (Phase 1) or oversell capability that doesn't exist (Phase 2 numeric).

The fastest path to GREEN is roughly half a day of writing (README rewrite + Phase 1 promotion + CTA) plus one or two days of evidence generation (run Phase 1 on real outputs from 3+ tools, build one minimum-viable numeric worked example or honestly remove the numeric claim).
